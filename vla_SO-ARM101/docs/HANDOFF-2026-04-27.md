## What ships in this commit

### Real-hardware data layer (proven end-to-end)
- **`jointstatereader`** read-failure fallback fixed — was snapping to tick `2048` (=0 rad) on transient read failures, causing visible RViz jitter; now falls back to `last_known_ticks`.
- **`trajectory_shim`** new node: hosts `/arm_controller/follow_joint_trajectory` and `/gripper_controller/follow_joint_trajectory` action servers. Time-interpolates incoming trajectories at 20 Hz on `/joint_commands` (which `jointstatereader` writes to the Feetech follower). Hybrid completion: time + 3° position tolerance + 1.5 s timeout. **Preemption fix:** newer goals abort the in-flight one via `goal_handle.abort()` (was `canceled()` which is invalid from `EXECUTING` state and produced rclpy state-machine errors).
- **`backend_real.launch.py`** wiring: trajectory_shim spawns when `read_only:=false`; `velocity_scale_real` LaunchArg (default 0.25) lets first-contact tests run slow.
- **Verified motion**: RViz Plan & Execute to home moved the physical SO-ARM101 follower with `max_err=0.18°` (gripper). control_gui FK tab also drives the arm via cancel-then-resend.

### Servo tuning (residual-error fix)
- **`P_Coefficient` raised 16 → 32** on all 6 servos (Feetech default) via one-off helper `feetech_set_pid.py`. lerobot's `so_follower.configure()` deliberately sets P=16 to make leader arms easy to back-drive — too soft for the follower under MoveIt position control. Closed shoulder_lift's gravity-sag from 3.6° → reachable within 1°.
- **Caveat**: lerobot rewrites P=16 on every `lerobot-calibrate`. Long-term fix is patching `lerobot/src/lerobot/robots/so_follower/so_follower.py:161` from `16` to a higher value, OR adding a "Re-tune PID" button to control_gui's Settings tab that runs the helper.
- **Calibration**: lerobot wrote the existing JSON to servo EEPROM (user pressed Enter to use existing file rather than `c` to recalibrate). 6/6 servos now match the JSON's `Homing_Offset` values.

### control_gui real-mode UI
- **New "Settings" tab**:
  - Real Hardware Calibration section: launches `lerobot-calibrate` wizard with copy-able commands + per-step "Open in Terminal" via osascript; "Check servo offsets vs JSON" reads register 31 in-process and shows match/diff per joint.
  - Real Hardware Connection section: **Connect** (jsr_write + shim), **Refresh** (re-detect USB + reconnect), **Disconnect** (orphan shim, jsr in observe-only).
- **Auto-detect at boot**: `_real_arm_detected_at_init` checks for `/dev/tty.usbmodem*` (macOS) or `/dev/ttyACM*` (Linux); flips Sim/Real radio to **Real Hardware** when arm is present. Auto-Connect fires 3 s after Settings tab loads.
- **`_ext_cmd_callback` early-return in real mode**: `/joint_commands` is now the wire to the Feetech follower (published by trajectory_shim). control_gui used to re-dispatch every shim publish as a `FollowJointTrajectory` goal — feedback loop that preempted every Plan & Execute trajectory. Killed.

### SIGBUS mitigations (partial — see open bug)
- **`OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES`** in `/tmp/run_core_real.sh`: macOS Foundation refuses fork() in a Tk-loaded multi-threaded process; `subprocess.Popen` from `_real_connect_worker` triggered the abort. Setting the env var lets fork+exec proceed.
- **Topic-swap subscriptions orphaned, not destroyed**: `_safe_orphan_subscription` replaces 4 `destroy_subscription` callsites (objects_sub, bbox_sub, _drop_sub) where the executor's spin thread races the destroy and SIGBUSes. Memory grows by one stale sub per topic-switch (bounded). Temp subs (cup-pose / lego-pose refresh) keep using `destroy_subscription` since those are per-button-click and would actually leak meaningfully.
- **Quickstart auto-refresh gated** on `not use_real_hardware`: the 800ms-after-tab-build `root.after(800, _cmd_qs_refresh_all)` was force-switching real subs to sim, then auto-connect's mode-flip ricocheted them back. Disabled in real mode.

**Already ruled out (none of these fixed it)**:

- subprocess.Popen fork-safety (env var set)

- `_on_tab_changed` handler (returns early for non-IK tabs)

**Next concrete step (untested)**: change `tk.Listbox(left, height=16, font=('TkFixedFont', 10))` at `control_gui.py:3592` to `font=('Menlo', 10)`. Hypothesis: macOS Tk's named-font alias resolution invokes CoreText on the redraw thread, racing rclpy's MultiThreadedExecutor spinning at 20 Hz. Real Test tab has the same pattern and exhibits the same crash. Fix is one line per listbox; if validated, applies to both tabs.
